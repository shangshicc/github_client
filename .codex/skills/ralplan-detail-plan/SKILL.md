# Ralplan 细化实施方案

## 角色边界

将 `ralplan` 的最终方案继续细化为**可落盘、可交接、可验证、低歧义**的中文工程实施蓝图。本 Skill 不替代 `ralplan` 做总体取舍；只在总体方案已存在时做二次拆解。

## 不变量

- 输出使用中文，术语统一使用“功能步骤”。
- 以 ralplan 最终方案为唯一主输入；必须区分“原方案依据”“工程化补全”“合理推断”。
- 默认写入 `.omx/implementations/<slug>-detail-plan.md`，并在最终回复说明保存路径。
- 至少拆为 3 个功能步骤，优先 3~6 个；按功能职责拆，不按“分析/开发/测试”流水账拆。
- 每个功能步骤必须能继续交给工程师、`ralph`、`team`、`ultraqa` 或 goal-mode 执行。
- 当前项目无 CI/CD 配置；除非输入方案明确要求，否则不要默认加入 CI/CD 步骤或配置。
- 若当前环境不支持 OMX runtime workflow，只把 `ralph` / `team` / `ultraqa` 写作后续建议执行方式，不声明已启动。

## 渐进式披露导航

| 需要做什么 | 读取什么 |
|---|---|
| 生成或改写 detail plan | 先读 `references/detail-plan-contract.md` |
| 需要完整 Markdown 骨架或步骤字段顺序 | 再读 `templates/detail-plan-template.md` |
| 只判断是否应使用本 Skill、或解释职责边界 | 仅读本 `SKILL.md` 即可 |

## 执行流程

1. **解析输入**：优先使用当前对话中最近的完整 ralplan；其次使用用户粘贴内容、显式文件路径、`.omx/plans/` 下最新且像最终方案的文档。
2. **确认基线**：提炼总目标、关键功能块、约束、不变量、风险、验证要求和建议执行路径；输入不完整时标注缺口并继续合理细化。
3. **生成文件名**：有源文件时用 `<源文件名去扩展名>-detail-plan.md`；纯文本输入时用标题或目标生成 kebab-case slug；仍不稳定时用 `ralplan-detail-plan-<YYYYMMDD-HHMM>.md`。
4. **拆成功能步骤**：输出 3~6 个可执行职责单元；UI 视觉相关内容存在时，至少拆出 1 个 UI 视觉功能步骤。
5. **补全执行契约**：为每个步骤补来源依据、目标、范围边界与非目标、输入、工程动作、推荐执行方式、输出、不变量、依赖、测试场景、风险与回归点；复杂步骤补 Mermaid。
6. **补总体验证闭环**：说明关键路径、并行项、里程碑、总体验证、回归关注点、执行方式汇总和下一条可直接执行的 prompt。
7. **落盘并回复**：创建 `.omx/implementations/`（如不存在），写入完整 Markdown；最终回复只总结输入来源、保存路径、验证/假设和后续建议。

## 质量门槛

生成前按 `references/detail-plan-contract.md` 自检：

- 每个步骤动作落到工程对象，例如目录、文件、类、组件、Provider、接口、路由、状态流、数据模型或构建产物。
- 测试场景必须有业务语义名称，并包含“前置条件 / 测试步骤 / 预期结果”；风险与回归点只登记风险、影响面和回归焦点，不重复测试步骤。
- Mermaid 只给复杂步骤；简单步骤说明省略理由。
- 不复制 ralplan 原文凑篇幅，不使用“优化相关逻辑”“完善流程”“处理异常”等无对象表述。
- 最终文件可以直接作为执行代理的交接输入。

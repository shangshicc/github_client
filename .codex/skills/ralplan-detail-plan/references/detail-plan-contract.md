## 输入与落盘

输入优先级：

1. 当前对话最近一次完整 ralplan 最终方案。
2. 用户显式粘贴的 ralplan 或等价总体方案。
3. 用户显式提到的 `.omx/plans/*.md`、PRD、test spec 或 handoff 文件。
4. `.omx/plans/` 下最近修改且文件名包含 `final`、`scheme`、`approved`、`reevaluation` 等最终方案信号的文件。

存在多个候选时，选择最新且内容最完整的版本，并说明选择依据。输入不足时仍继续，但要标注：来自原方案的内容、合理推断、待补充项和需回仓库/原方案核实项。

落盘规则：

- 默认目录：`.omx/implementations/`。
- 默认文件名：`<原始 ralplan 文件名去扩展名>-detail-plan.md`。
- 纯文本输入：优先用标题生成 slug；无标题则用总目标提取 3~8 个关键词；仍不稳定则用 `ralplan-detail-plan-<YYYYMMDD-HHMM>.md`。
- 保存后在最终回复中写明路径，并说明“已按实施方案标准落盘”。

## 拆分规则

- 至少 3 个功能步骤，默认 3~6 个；复杂方案可更多。
- 按功能职责、系统责任边界、数据流转或执行依赖拆分；不要只按时间阶段拆。
- 步骤名体现职责，例如“认证失效状态回收”优于“异常处理”。
- UI 视觉、交互或动效是重要内容时，单独拆出 UI 视觉功能步骤。
- 每个步骤都是可交接执行单元，且粒度尽量均衡。
- 当前项目无 CI/CD 配置；除非输入明确要求，不要新增 CI/CD 步骤。

## 功能步骤字段

每个步骤必须包含：

1. 来源依据：分别列原始 ralplan、工程化补全、合理推断。
2. 目标：写可达成的功能目标。
3. 范围边界与非目标：用同一节说明包含项、排除项、移交到后续步骤的事项；不要再单独开“非目标”节。
4. 输入：代码入口、依赖模块/文件、前置工程条件。
5. 执行动作：编号动作必须落到工程对象。
6. 推荐执行方式：直接执行、`analyze`、`ralph`、`ralplan`、`team`、`ultraqa` 或 goal-mode，并说明原因。
7. 输出：变更文件、产物、预期行为变化。
8. 兼容性与不变量：必须保持不变的行为、兼容性要求、回归关注点。
9. 依赖与衔接：上游依赖、下游影响、联动检查点。
10. 测试用例：按本契约的测试场景格式给出。
11. 风险与回归点：只登记风险、影响面、脆弱位置、回归焦点和缓解建议，不重复测试步骤。
12. 流程图：按复杂度决定是否提供。

## 字段去重原则

- **范围边界与非目标**：非目标是范围边界的排除项，不是独立信息源；合并为一节，分别写“本步骤包含 / 本步骤不包含 / 移交后续步骤”。
- **测试用例与风险回归点**：测试用例回答“怎么验证”；风险与回归点回答“哪里可能坏、坏了影响什么、回归要盯哪些既有行为”。风险节不得复制测试用例的前置条件和操作步骤。
- **兼容性与回归关注点**：兼容性写必须保持的不变量；风险节只引用需要关注的脆弱区域，避免重复列完整不变量。

## 测试场景契约

- 默认每个功能步骤给 3 个及以上测试场景。
- 简单、无分支、无异步、无权限差异、无状态流转的步骤可降为 2 个高价值场景，但必须说明原因。
- 场景命名体现业务语义和风险点，禁止“场景一”“正常情况”。
- 优先覆盖业务主链路、关键状态切换、失败回退、权限差异、空/脏数据、并发与幂等。
- 每个场景都包含：
  - 前置条件：数据、账号权限、路由入口、功能开关、Mock、接口返回、缓存或设备环境。
  - 测试步骤：按顺序写用户操作、触发动作、状态变化或验证动作。
  - 预期结果：可观察、可判定；落到 UI 状态、字段值、接口行为、缓存变化、路由跳转、提示文案、日志或不应发生的副作用。
  - 建议验证层级：可选，写单元测试、组件测试、集成测试、页面 smoke、手工回归等；不适合自动化时说明原因。

注意：步骤“输入”里的前置工程条件，不等同于测试场景的运行前置条件，不要简单复制；测试场景也不要复制“风险与回归点”的风险描述。

## Mermaid 规则

满足任一条件必须提供 `flowchart TD` 或 `flowchart LR`：

- 执行动作达到 3 个及以上。
- 包含判断、失败回退或降级分支。
- 存在异步状态流转。
- 存在跨模块、跨角色或跨系统协作。

图表建议 4~8 个节点，体现开始、关键动作、判断分支和输出。简单步骤可省略，但要写明“无分支/无异步/动作少，因此省略”。

## 推荐执行方式

选择最轻但足以保证质量的执行面：

| 情况 | 推荐 |
|---|---|
| 只读分析、影响面确认、证据收敛 | `analyze` |
| 边界清楚、范围较小、一轮可收敛 | 直接执行 |
| 多文件改动、需要持续修复与验证闭环 | `ralph` |
| 仍缺少边界或存在多方案取舍 | `ralplan` |
| 多条独立子线可并行推进 | `team` |
| 以测试、复现、修复、回归收敛为主 | `ultraqa` |
| 长期目标、有多阶段验收 | goal-mode |

当前环境不支持 runtime workflow 时，也可以作为“后续建议执行方式”保留。

## 风险与回归点契约

每个步骤的风险节只写：

- 主要风险：实现、协作、数据、权限、状态、兼容性或性能层面的失败模式。
- 高风险位置：具体文件、模块、接口、Provider、路由、状态流或 UI 区域。
- 回归重点：最容易被本步骤破坏的既有行为或跨步骤联动。
- 缓解建议：可选，写预防动作、代码审查关注点或验证优先级。

不要在风险节复写测试用例步骤；如需关联测试，只写“由测试场景：<名称>覆盖”。

## 总体验证闭环

所有步骤后补充：

- 整体验证方式。
- 关键里程碑。
- 关键路径与可并行项。
- 总体兼容性与回归关注点。
- 各步骤推荐执行方式汇总。
- 是否适合交给 `ralph`、`team` 或 goal-mode。
- 一条可直接复制执行的下一步 prompt。

## 最终回复

落盘完成后，最终对话回复保持简短，包含：

- 使用的 ralplan 输入来源。
- 保存路径。
- 是否已按实施方案标准落盘。
- 主要假设或输入缺口。
- 推荐下一步。

## 反模式

避免：

- 直接复制 ralplan 原文而不细化。
- 用“分析 / 开发 / 测试 / 部署”作为唯一拆分。
- 流程图与文字动作不一致，或给简单步骤硬画无信息量图。
- 执行动作没有工程对象。
- 测试用例只有标签，没有前置条件、步骤和可判定预期。
- 风险与回归点复制测试步骤，或没有说明失败模式、影响面和回归焦点。
- 未说明兼容性、不变量或回归重点。
- 在当前无 CI/CD 配置的项目里默认加入 CI/CD 工作。

## 基本顺序

推荐顺序：

1. 开发实现
2. 构建 / 打包
3. 单元测试
4. UI 测试
5. 集成测试
6. lint / 静态分析

## 变更类型与测试层级

### 纯逻辑 / 数据层

- 优先单元测试
- 补必要的回归测试
- 之后跑 lint 和构建

### UI / 页面交互

- 优先 widget / UI 测试
- 对关键状态切换补单元测试
- 之后跑构建和 lint

### 跨页面 / 外部协作 / 启动链路

- 优先集成测试
- 视需要补 UI 或单元测试
- 之后跑构建和 lint

### 影响平台打包或运行时边界

- 集成测试优先
- 平台相关构建必须跑
- lint / 静态分析必须跑

## Flutter 常用命令

- 单元 / UI 测试：`flutter test`
- 指定测试：`flutter test <path-or-pattern>`
- 静态分析：`flutter analyze`
- 平台构建：`flutter build <target>`

`<target>` 以本次变更影响的平台为准，例如 `macos`、`android`、`ios`、`web`、`windows`、`linux`。

## 通过标准

- 相关测试通过
- 构建通过
- lint / 静态分析通过
- 读取输出确认不是“命令跑完了”而是真通过

## 失败处理

- 任何一步失败都先修复，再重跑同一步
- 连续 3 次仍失败时，把问题写入 `.omx/question/`，并在回复中输出问题摘要
- 如果当前环境无法跑某个构建，说明原因，并补齐最接近的测试与 lint 证据
- 不要用口头判断替代验证输出

## 问题记录格式

当同一问题连续 3 次仍失败时，建议记录：

- 文件名：`.omx/question/{slug}-{YYYYMMDD-HHMM}.md`
- 模板参考：`templates/question-template.md`
- 只保留简短事实，避免长篇分析
- 回复中必须同步给出该文件路径和一句话问题摘要
